MCP server and tools

rdv-mcp: a stdio MCP server that gives an MCP client (Claude Code, Claude Desktop, the MCP Inspector) a Rendezvous agent. PLAN.md §6.1, SPEC.md §13.

The server runs one long-lived listening agent in-process. Its state is the same home dir as the rdv CLI (agent.json, config.json, inbox.jsonl, negotiations.json, lock, plus consent.json, events.jsonl and listener.lock), and it takes the lock only per operation, like rdv listen. So rdv contact pending or rdv contact grant can run in a terminal against the same profile while the server is up. Only one process per home consumes inbound events (whoever holds listener.lock); if rdv listen or another rdv-mcp already does, this server runs attached: its tools work, and rdv_inbox reads the events the consumer writes to events.jsonl. It takes over when the consumer exits. rdv_status says which (inbound: consumer or attached). See impl/README.md.

npm run build                              # from impl/
node packages/mcp/dist/src/bin.js --home ~/.rendezvous/omer --calendar cal.json --tz +02:00

Options: --home <dir> or --profile <name> (same resolution as rdv: --home, $RDV_HOME, ~/.rendezvous/<profile>), --calendar <file.json>, --calendar-dir <dir> (repeatable, env RDV_CALENDAR_DIR: where the assistant may pick other calendar files from), --window "next week evenings", --tz +02:00 (env RDV_CALENDAR, RDV_WINDOW, RDV_TZ). Without a calendar, incoming dinner proposals are listed but not answered. stdout carries MCP; human-facing notices go to stderr. Client config examples: impl/demo/SCRIPT.md.

Use it from Claude Code (plugin)#

The repo is also a Claude Code plugin marketplace. In Claude Code's chat:

/plugin marketplace add omernesh/rendezvous
/plugin install rendezvous@rendezvous
/reload-plugins

The plugin (plugins/rendezvous) registers this server through a small launcher (bin/rdv-mcp.mjs, run with node, so it works on Windows too) that loads the build the installer made in ~/.rendezvous/src (or $RDV_DIR). It adds the Rendezvous skill (install, identity, contact, first message, incoming requests) and a PreToolUse consent guard (below). The server uses the same home as rdv: $RDV_HOME, else ~/.rendezvous/$RDV_PROFILE, else ~/.rendezvous/default. The skill alone, for other agents that load SKILL.md files: npx skills add omernesh/rendezvous.

Use it from other MCP clients#

Per-agent setup, skill install and a check that it works for ten agents: docs/agents.md.

Register rdv-mcp as a stdio server; the installer puts it on PATH. Pass options (--profile omer, --calendar cal.json, …) in args.

Claude Desktop (claude_desktop_config.json) or Cursor (~/.cursor/mcp.json or .cursor/mcp.json):

{
  "mcpServers": {
    "rendezvous": { "command": "rdv-mcp", "args": ["--profile", "omer"] }
  }
}

Codex (~/.codex/config.toml):

[mcp_servers.rendezvous]
command = "rdv-mcp"
args = ["--profile", "omer"]

On Windows rdv-mcp is a .cmd shim, which most clients can't spawn directly: use "command": "cmd", "args": ["/c", "rdv-mcp", "--profile", "omer"], or "command": "node" with the built file (%USERPROFILE%\.rendezvous\src\impl\packages\mcp\dist\src\bin.js) as the first argument. Claude Code without the plugin: claude mcp add rendezvous -- rdv-mcp --profile omer (Windows: claude mcp add rendezvous -- cmd /c rdv-mcp --profile omer).

Approval forms need a client that supports MCP elicitation; Claude Code does in interactive sessions (not in -p). Elsewhere approvals use the confirm phrase the human reads in their own terminal (rdv contact pending), below.

Tools#

Tool Input Output
rdv_init profile, emails[], phones[] (email / phone: one of each, kept as aliases), relays (omitted: the default public relays wss://nos.lol, wss://relay.primal.net, wss://relay.nostr.net, wss://nostr.oxtr.dev), public_pointer, calendar, window, tz agent ID, fingerprint; keeps an existing agent and its relays (re-key only with rdv init --force). Every address is public; at most 8
rdv_addresses action list / add / remove, address, public (add; default true) our addresses, each public or private; add / remove re-sign and (pointer on) republish the card and re-subscribe at once, like rdv address. The owner's own setup, not a consent decision; strict email / E.164 only; contacts are kept
rdv_status — ID, our addresses (addresses, and our_addresses with public or private), relays, relay_health (per relay: last_ok, last_error with kind and the relay's message as untrusted_peer_text, cooldown_until), contacts (local_label: what your user called them; unverified_claims: the addresses their cards claim; label_conflict when two share a label), pending count, negotiation settings, approval mode
rdv_publish_card — topics published, and on_relays: per public address, whether the relays now serve this card (read back)
rdv_discover address cards found (agent ID, fingerprint, claimed addresses, relays); never a label (anyone can publish a card for any address), never our own card (for our own address: own_card_on_relays)
rdv_request_contact target (email, +phone, or agent ID), greeting, label (probes only) request ID, local_label (a probe: the address probed, applied only when the human confirms the answer; by agent ID: none, and a label is refused)
rdv_pending_requests — requests with fingerprint, binding, how they arrived, untrusted greeting
rdv_grant request_id, tier, may_propose_meetings, invoke, confirm_phrase, label; or grant_id (+ confirm_phrase, label) to confirm a probe answer; or agent_id (+ tier, may_propose_meetings, invoke, confirm_phrase) to grant an existing contact more, which also sends it a reverse grant contact (needs the human, below)
rdv_revoke agent_id, or request_id / grant_id (+ block) to decline revoked / declined / rejected
rdv_send agent_id or to (a local_label), payload {type, …} (not a2a/*, rdv/*) agent ID, fingerprint, envelope seq; to is refused when no contact, or more than one, has that label
rdv_inbox since cursor, limit, wait_seconds (≤ 60) events + next_cursor
rdv_negotiate action propose / confirm / cancel / status; agent_id, intent dinner, window, calendar, tz, minutes, place, area, expires, task_id, reason, confirm_phrase task ID and state; progress via rdv_inbox; confirm needs the human (below)

Resource rdv://inbox holds the latest 50 events; the server supports resources/subscribe and sends notifications/resources/updated when events arrive, so a client that subscribes needn't poll.

Events: contact_request, contact_candidate (an answer to our discovery probe, confirmed through the same human gate as a grant), contact, message, revoked, dropped, error, reverse_grant (what a contact's human now lets us do: may_propose_meetings and invoke, the capability URIs), and dinner (kind proposed / offer-received / countered / confirm-needed / accepted / completed / released / rejected / canceled / expired / status, with a plain-language summary we write from validated fields; confirm-needed also carries a next_step).

Grants issued here always carry may_initiate: true, may_access_calendar: "free_busy", max_frequency: "100/day", and may_propose_meetings (default true), and scope.invoke (NOTES 74): the meeting capabilities when meetings are allowed, plus exactly the capability URIs passed in invoke, nothing else (deny by default, no wildcard). The form names those capabilities with one checkbox, and a confirm phrase approves only the list it was shown with. The calendar adapter only ever shares free slots, never titles.

Consent: the human decides (demo-critical)#

rdv_grant must not succeed on the model's say-so. It succeeds only through one of these:

  1. Elicitation. If the client advertises the elicitation capability, the server asks the client to show the human a form: requester agent ID, fingerprint, binding (with a warning that claimed proves nothing), how the request arrived, the greeting marked untrusted, a tier picker, and the local label (the model's suggestion, editable; empty for none). Only accept with approve: true grants; the human's tier and label win over the model's. The model never sees or answers this form. A probe answer gets the same form, with the probed address as the label.
  2. Confirm phrase. Otherwise each pending request gets a random phrase (three words and three digits, about 28 bits), shown only on human channels: this server's stderr and rdv contact pending in text mode (not --json). consent.json (mode 600) keeps only a salted scrypt hash, so the terminal issues a new phrase each time it shows one (the latest shown wins). The human reads it and types it to the model, which passes it as confirm_phrase. A phrase approves the request on the terms shown with it (tier, scope and local label, default first: no label): if the model asks for another tier, may_propose_meetings or label, it is refused and the human is shown a new phrase for exactly those terms (issue #12, NOTES 62). A probe answer's phrase is bound the same way to its label (the probed address unless the model asks for another). Phrases are per request and single use; 5 wrong tries replace the phrase. A phrase can approve tiers friend and below; family/spouse need the form or rdv contact grant --tier … in a terminal.
  3. The terminal. The human runs rdv contact grant <id> themselves.

Each meeting too (issue #8). The server answers dinner proposals from the calendar, but the slot it picks is only held tentatively ("confirm-needed") until the human confirms it: rdv_negotiate with action confirm passes the same gate. With elicitation the human gets a form (peer fingerprint, time, place marked untrusted); decline there cancels the negotiation and releases the hold, dismissing it leaves the dinner held. Otherwise the server issues a confirm phrase per held dinner (same rules, shown on stderr and in rdv dinner list text mode), or the human runs rdv dinner confirm <task-id> --hold <code> (or rdv dinner cancel) in a terminal. That happens once per side: the accepter's human before the accept goes out, the offerer's before the meeting/confirm. Holds are released on cancel, decline or expiry. Approval is bound to the meeting the human saw, not the peer-chosen task ID: if the held meeting changes before the confirm runs (another slot, peer or stage, or a new negotiation under the same ID), nothing is confirmed, the tool says it changed, and a new phrase is issued (NOTES 59).

Each task from a contact, twice (issue #24). rdv_task routes general tasks (SPEC §7.6). A contact's task under a confirm or free-form capability (the general request/v1 is free-form) waits until the human approves its start ("approve-start"); notify tasks are only shown, auto ones start on the grant and are written to audit.jsonl. Whatever the agent sends back ("submit") waits again until the human releases it ("approve-release"), whatever the class, since the model wrote it. Same gate as a grant: a form showing the task (peer text marked untrusted) or the draft, or a confirm phrase per gate (stderr and rdv task list text mode), or the human runs rdv task approve <task-id> --code <code> / rdv task release <task-id> --code <code> in their own terminal. Each is bound to a digest of what the human saw: a re-request under the same task ID, or a changed draft, approves nothing (NOTES 76).

Auto-approve (issue #25). The human can put one trusted contact on auto_approve: all from their own terminal (rdv contact auto-approve <contact> all [--until 7d]); that contact's tasks then start and their results leave without a form or phrase, each pass written to audit.jsonl. No tool sets or extends it: rdv_status (per contact auto_approve, until when, how many actions it passed) and rdv_task only show it, and rdv_inbox reports auto_approved starts and an auto_approve_off event when it ends (NOTES 77).

Canceling an agreed dinner (issue #20). rdv_negotiate action cancel on a completed dinner passes the same gate, bound to the agreement shown (NOTES 61): a form if the client can elicit (only an explicit yes cancels), otherwise the first call issues a cancel phrase to the human (stderr and rdv dinner list) and fails; the human can also run rdv dinner cancel. The peer's agent frees the evening without asking (it only frees time) and reports a meeting-canceled event.

Granting an existing contact more (issue #1). rdv_grant with agent_id gives a contact (for example one the user requested, which by default may write but not propose meetings) the tier and may_propose_meetings asked for, and sends it a reverse grant so it can use them. Same gate: a form showing the contact's fingerprint, local label, its rights now and exactly what is granted (the human's tier and meetings choice win), or a confirm phrase issued on the model's first call and bound to that contact and those terms (stderr and rdv contact pending). The contact is checked again under the lock where the grant happens; one revoked and made again under the same agent ID is refused (NOTES 66).

No tool result ever contains a phrase (tests scan every result and the inbox resource). Limits (NOTES 57): phrases are not on disk, but a model that can read files or run commands as the same user can still catch one while it is shown (or run rdv contact pending itself); there, prefer elicitation or the terminal. Without a phrase or elicitation, rdv_grant fails and tells the model to ask its human.

Threat model. This stops a model from granting on its own initiative, and stops instructions injected through peer text from making it grant. It does not stop a model that can run arbitrary shell commands or read arbitrary files as the same OS user: such a model can catch a phrase while it is shown, run rdv contact grant or rdv contact label itself, or read agent.json, which holds the secret key, a worse problem. In Claude Code, keep the default permission mode (shell commands and reads outside the project need approval) and add deny rules for the home dir and rdv contact pending (example in demo/SCRIPT.md). The Claude Code plugin adds a PreToolUse hook (plugins/rendezvous/hooks/consent-guard.mjs) on every tool that refuses the consent and phrase-showing rdv commands (contact grant/confirm/resync/ label/pending, contact request <agent-id> --label, dinner confirm/ cancel/list, listen --auto-grant/--auto-confirm, init --force), any command naming agent.json, agent.json.bak or consent.json, and any read, edit, search or glob of a Rendezvous home. It parses commands like a shell before matching. It is defence in depth, not a security boundary: a model with a shell can still get a command past it (NOTES 62). The boundary is the consent gate above. The strongest setup runs rdv-mcp as a different OS user, or on another machine, from the one the assistant's tools run as. Revoking and declining need no confirmation: they only reduce access.

Prompt injection gate#

  • Peer-written text (greetings, text parts, decline reasons, free-form message payloads, error and drop details) reaches the model only as {"untrusted_peer_text": "…"}, with control and bidi characters replaced and a 2000-character cap. Results that contain such fields start with a note telling the model to treat them as data. The server instructions and the tool descriptions say the same.
  • Short peer-chosen fields are strict tokens or get quarantined the same way: agent IDs, UUIDs, addresses (email / +phone), relay URLs, tiers, bindings, task states, payload type ([a-z0-9][a-z0-9._/-]{0,63}), integer seq.
  • Only data parts drive the negotiation engine (@rendezvous/a2a, strict validation); text parts are display only.
  • The model can't make the server read local files: rdv_request_contact takes addresses and agent IDs (no card files), calendar paths must end in .json and resolve (symlinks included) inside the home, the --calendar directory or a --calendar-dir, the file must be a strict calendar (busy list, optional timezone, nothing else) before it is read or rewritten, and calendar errors never echo file contents.
  • Errors that could quote peer or file content (inbound handling, fs and JSON parse failures) go to the server log for the human; the model gets a generic line. Only our own messages (bad input, negotiation rules) reach it.

Tests#

npm test -w @rendezvous/mcp: two servers (Omer, John) driven by the SDK's Client over an in-memory MCP transport against the in-memory relay, covering init → discover → request → refused grant → human approval (confirm phrase, and elicitation accept / decline) → negotiate → refused model-only dinner confirmation → each human confirms (phrase, form) → completed on both sides, plus

a stdio smoke test, phrase rules and hardening. The chat onboarding flow the plugin's skill follows (init, request by address, both humans approve by form or phrase, first message) runs the same way. test/plugin.test.ts checks the plugin: manifests, the launcher over stdio, the consent guard, and a lint that fails if the skill or its references tell the assistant to run a consent command. Live (dinner and onboarding): RDV_LIVE_RELAYS=wss://nos.lol,wss://relay.primal.net npm run test:live -w @rendezvous/mcp.
