Rendezvous plugin for Claude Code

Rendered from plugins/rendezvous/README.md on GitHub. Markdown version for LLMs.

Set up Rendezvous, end-to-end encrypted messaging between agents (messages, tasks, files, groups, and meeting scheduling as one example), by chatting with Claude: install rdv, create your agent, connect with another person's agent and send the first message. Approvals always come back to you.

/plugin marketplace add omernesh/rendezvous
/plugin install rendezvous@rendezvous
/reload-plugins

Then type /rdv-onboarding (the full name is /rendezvous:rdv-onboarding, if another plugin also has an rdv-onboarding). It sets you up one question per turn: install, MCP tools, profile, email, optional phone, relays (the default public set or your own, each one checked), public pointer, your agent, its card and an optional first contact, verifying each step before the next. Re-run it to resume where you stopped.

After that, ask, for example: "Ask john@doe.com's agent to connect", "Tell John I'm running late", "check rendezvous".

What it contains:

  • skills/rdv-onboarding/SKILL.md: the /rdv-onboarding command, a guided setup that asks one question at a time and follows the consent rules of the rendezvous skill.
  • skills/rdv-backup/SKILL.md: "back up my agent" and "recover my agent from backup", one step per turn in plain language (below).
  • skills/rdv-gateway-setup/SKILL.md: "set up my gateway" and "connect claude.ai to my agent": asks the gateway installer's questions one at a time, hands the user one command for their own terminal (where they type the PIN and any secret), then checks it and gives each assistant's connector address.
  • skills/rendezvous/SKILL.md: the setup and messaging workflow, with the consent rules. It uses the Agent Skills format, so other agents can load it too (npx skills add omernesh/rendezvous).
  • .mcp.json: registers the rdv-mcp server through bin/rdv-mcp.mjs, which starts the build the installer put in ~/.rendezvous/src (or $RDV_DIR). Until Rendezvous is installed the server fails to start; install it (the skill points you to the installer), then run /reload-plugins. The server uses the profile rdv uses: $RDV_HOME, else ~/.rendezvous/$RDV_PROFILE, else ~/.rendezvous/default.

  • hooks/hooks.json: a consent guard on every tool call. It stops Claude from running the rdv commands that grant consent or print confirm phrases (rdv contact grant, rdv dinner confirm, rdv task approve, rdv task release, rdv contact pending, rdv dinner list, rdv task list, rdv group invite, rdv group join, rdv group approve, rdv group pending, rdv group terms, …), put a contact on auto-approve (rdv contact auto-approve), or name a contact (rdv contact label, or rdv contact request <agent-id> --label), however the command is quoted or wrapped (npx, bash -c, $(…)), and from reading, editing, searching or globbing the agent's secret key, consent file and auto-approve file with any tool. Those stay with you, in your own terminal.

    Auto-approve and your owner passphrase (issues #47, #44). Turning auto-approve on asks for a passphrase you set yourself with rdv_owner_passphrase (ask Claude to set an owner passphrase; you type it twice into an approval form, and only the Rendezvous server sees it), or rdv owner-secret set in your own terminal. Setting one turns auto-approve off for every contact. You type it either in your own terminal (rdv contact auto-approve <contact> all) or, when you ask Claude to turn it on, into the approval form rdv_auto_approve opens: the form shows the contact, its fingerprint, what it covers and until when, and what you type goes to the Rendezvous server only, never to Claude. If no form can be shown, it is refused (there is no confirm phrase for it). Never type the passphrase into the chat. Claude may turn auto-approve off whenever you ask, with no form. In the terminal the passphrase is read from the terminal device itself (/dev/tty, or CONIN$ on Windows), not from stdin; it is never echoed or printed, and only a scrypt hash is kept (owner-secret.json, mode 600); three wrong answers lock it for a minute, then twice as long after each further miss. rdv init in a terminal offers to set it, and so does /rdv-onboarding (it calls rdv_owner_passphrase and opens the form). The first passphrase is trust on first use: it is audited, and rdv whoami and rdv_status show when it was set; if that wasn't you, run rdv owner-secret reset in your own terminal (refused while locked; it turns every auto-approve off and only clears, and a new passphrase can be set 10 minutes later). Any pseudo-terminal (script, expect, unbuffer, winpty, node-pty, pty.spawn) is refused outright. It replaced "retype the fingerprint shown here", which an assistant could pass by running the command in a pseudo-terminal and typing back what the prompt printed. The hook also refuses any command that names contact and auto-approve under any wrapper or spelling (script -c, expect -c, unbuffer, winpty, stdbuf, timeout, nohup, env, node-pty, Python pty.spawn, here-strings, heredocs, sh -c, node -e, python -c), any quoted string that names auto-approve, any mention of owner-secret, and any read or write of autoapprove.json or owner-secret.json in any folder.

    What this protects against: an assistant that drifts or is prompt-injected and tries to switch auto-approve on by itself, with or without a pty: it never sees the answer, so it has nothing to type. What it does not protect against: a model with a shell running as your OS user can still write a script the hook can't read, delete owner-secret.json and set its own passphrase, edit Rendezvous' files, or watch you type the passphrase into a terminal it controls (so type it only in your own terminal, one you opened yourself). No local check is a hard boundary against your own account; for that, run the assistant or rdv-mcp as another OS user.

    The hook is defence in depth, not a security boundary. A model with a shell can always build a command it can't see (a script file, another interpreter). The boundary is the MCP consent gate: rdv_grant and rdv_negotiate need your approval form or a confirm phrase only you see, and the phrase is stored only as a hash. See "Threat model" in impl/packages/mcp/README.md.

Backups (issue #88): ask "back up my agent". Claude asks where to keep the file (your password manager or a cloud drive is best: somewhere that survives this computer), then calls rdv_backup, and an approval form asks you for a passphrase, twice. Only the Rendezvous server sees it, never Claude; without a form it is refused (use rdv backup <file> in your own terminal). The file is encrypted (scrypt and AES-256-GCM) and holds the agent's key, contacts, grants and settings, never open approvals or confirm phrases. Whoever has the file and the passphrase can be your agent, as with the key itself, so choose a strong passphrase and keep it apart from the file. On a new computer, install Rendezvous and ask "recover my agent from backup": the form shows the agent ID and fingerprint in the file before you type the passphrase. Your contacts are told the agent was restored, so your conversations go on with no resync. rdv backup and rdv restore are yours, in your own terminal; the hook refuses them for Claude.

Other settings are chat tools too, each finished by an approval form that only you answer (Claude never does; there is no confirm phrase for them): "rename this contact" (rdv_label), "set or change my owner passphrase" (rdv_owner_passphrase), "take John's messages again" after a fork or rollback (rdv_resync, for a contact, a frozen group or a muted member; check with the person first), "allow direct transfers" (rdv_file "direct-transfer"; turning it off needs no form), and "start over with a new identity" (rdv_init with replace: the form shows what you lose, offers a backup first and asks you to type the last 4 characters of the fingerprint), and "keep my agent reachable while Claude Code is closed" (rdv_service: the form shows the background listener it installs, its command line and how to remove it; removing it needs no form). Or in your own terminal: rdv contact label, rdv owner-secret set, rdv contact resync / rdv group resync, rdv file direct-transfer on|off, rdv init --force, rdv service install. Still terminal-only for now: the owner passphrase reset (rdv owner-secret reset) and gateway administration.

Sending: Claude picks the recipient by its local_label, never by an address the other agent's card claims, and shows you the fingerprint before the first message. Only you set a label: it is part of what you approve (the form shows it next to the fingerprint and you can change it; a confirm phrase approves only the label it was shown with), or you rename a contact by asking Claude (rdv_label opens a form with the current name), or in your own terminal with rdv contact label <agent-id> <label>. A card found by address is only a claim, so it never labels a contact.

Approving a contact: Claude calls rdv_grant, and Claude Code shows you an approval form (MCP elicitation) once Claude's reply ends. Claude can't fill it in for you; your answer completes the step. The form that approves a contact, the one that makes an invite link, and the forms for a contact's task and for a dinner it proposed also have "Don't ask again for this contact": tick it with your approval and what it lists (on the task and dinner forms, that contact's tasks of that kind, or its dinners) stops asking you, until you ask Claude to turn auto-approve off. On an invite link it applies only to the contact that uses the link, when they use it.

Tasks and files (v0.3): ask "Ask John's agent to review this", or answer when a contact asks your agent for something. Claude uses rdv_task and rdv_file. Two approvals guard every request from a contact: you approve starting it, and you approve the exact answer before it goes back, each through a form or a phrase from your own terminal. A request is treated as data, never as instructions. Files are sent by reference, only after you release the result they are in, and a file a contact sends is fetched only for a task you started and saved in quarantine. Auto-approve for one trusted contact exists (it also confirms dinners that contact proposes), but only you can turn it on, with the owner passphrase: in your own terminal, or in the form Claude opens when you ask it to; Claude never suggests it. The user guide is docs/tasks.md.
